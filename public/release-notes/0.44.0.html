FinderGit 0.44.0

Release notes

FinderGit 0.44.0 — Cleaning: free the space your developer tools can rebuild

Highlights

  • A new Cleaning page. It sits under Account in the sidebar and finds the folders nobody wrote, the ones a tool makes again on its next run. On the Mac it was built on, the first scan found about 30 GB. The first visit scans your root folders, your home folder and every repository, and the cards land and count up as the results arrive. There are eight cards:

    • node_modules, for every JavaScript project.
    • Build output: .next, .nuxt, .svelte-kit, .turbo, .parcel-cache, dist, build, out, a Rust or Maven target, and more.
    • Swift & Xcode: SwiftPM's .build, CocoaPods, DerivedData, Xcode previews, device-support files, simulator caches, and simulators whose runtime is gone.
    • Package caches: npm, Yarn, pnpm, bun, Homebrew, Composer, CocoaPods, pip and Deno.
    • Toolchains: Go's build and module caches, Cargo, Gradle and Maven.
    • Python: virtual environments and the caches of pytest, mypy and Ruff.
    • Git objects: loose objects and garbage in each repository, repacked with Optimize, which keeps all history.
    • Other caches: browsers downloaded for tests, node-gyp headers, Electron and JetBrains caches.

  • You choose, folder by folder. Open a card to see each folder with its project, its size and when it last changed, then tick what to clean. Only what is safe, not in use and, inside a project, untouched for 30 days starts ticked. Anything else shows a badge with the reason and is left for you to decide:

    • a folder a dev server, a watcher or a terminal is working in, a monorepo's root included;
    • a folder changed recently;
    • a folder slower to get back, such as an Xcode build or a virtual environment.

    A folder you untick stays unticked when you scan again.

  • Only what a project can rebuild. Inside a repository, a folder is listed only when that repository's own .gitignore ignores it and it sits next to its project file, such as the package.json beside a node_modules. A folder holding a file you added to Git is never listed, nor is a symbolic link or anything inside .git. Each folder is checked again right before it is deleted: still ignored, still a real folder, still inside your root folder, and not something that started being used after you confirmed.

  • Honest sizes. Each size is what deleting that folder alone gives back. Package managers that fill node_modules from a shared store leave files the store still holds, so those are never promised as free space. The bar under the total shows your startup disk now and after cleaning.

  • Deleted for good, with a Stop. After one confirmation the ticked folders go, largest first, so stopping halfway has already freed the most it could. They are deleted, not moved to the Trash, because freeing the space is the point. A cache whose own tool knows it better is cleaned by that tool. Homebrew's downloads are emptied directly, never with a cleanup that would also remove old versions of your formulae. The result shows on the page and in the Activity panel.

Under the hood

  • Finding folders. The walk uses fts and follows a root folder that is itself a link, but nothing below it.
  • Ignore check. Each candidate inside a repository goes through that repository's own git check-ignore. A home folder that is itself a repository (dotfiles) vouches for nothing.
  • Sizes. A file's size is its APFS private size (ATTR_CMNEXT_PRIVATESIZE), so blocks shared through hard links or clones are not counted. A 327 MB pnpm store measured 95 MB of its own.
  • In use. A project is in use when a process's working directory is inside its repository, read with libproc. FinderGit's own git processes, which run inside the repositories it watches, are left out. Xcode, Simulator and a running brew are checked for the caches they hold.
  • Tool cleanups. pnpm store prune, go clean and npm cache clean are pointed at exactly the folder that was measured.
  • Simulators. They are deleted by the UDIDs that were measured, after simctl confirms again that they are still unavailable.
  • Safety net. Every path is validated against the catalog that produced it before anything is removed.

Install

  1. Download FinderGit-0.44.0.dmg
  2. Open the DMG and drag FinderGit into Applications
  3. Launch normally — the app is signed with an Apple Developer ID and notarized by Apple

Requirements

macOS 15 or later. Universal binary (Apple Silicon and Intel).
