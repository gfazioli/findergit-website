# Diff Viewer

FinderGit includes an inline diff viewer that shows changes for any modified file.

![Inline diff viewer with colored additions and deletions](/screenshot-feature-diff.png)

## Viewing a diff

### From the Detail Panel

When a repository is selected, open its **Changes** card: the changes list shows all modified files. Click on a **file name** (not the Stage/Unstage button) to load its diff. The selected file name turns blue, and the diff appears below.

### A commit's diff, in its own window

In the **Commits** card, expand a commit to list its files and click one: its diff for that commit opens in a window of its own, drawn the same way as the diff above. The window can be moved and resized, so you can keep it beside the commit list, and one file gets one window — asking for the same file again brings its window forward.

The window's header shows the file's path, the commit's short SHA and subject, and the +/− counts. **Wrap lines** in the header wraps long lines at the window's edge (on by default); turn it off to cut them there instead. **Esc** or **Space** closes the window. The window is read-only: nothing in it stages, discards or reverts.

### From file selection

When you select a single modified file in the tree view, the detail panel automatically loads and displays its diff.

## Reading the diff

The diff view shows:

- **Header** — file path and stats (+N additions / -M deletions)
- **Line numbers** — old line number (left) and new line number (right), in a gutter
- **Added lines** — a green edge, a green tint and a `+` glyph
- **Removed lines** — a red edge, a red tint and a `−` glyph
- **Context lines** — no background, showing surrounding unchanged code
- **Hunk bands** — each hunk sits under a band that gives the lines it covers and the function or type it is in, instead of git's raw `@@ -start,count +start,count @@` line

Git's own header lines (`diff --git`, `index`, `---` and `+++`) are not shown: the header above the diff already names the file.

The diff scrolls vertically for large diffs. A line too long for the panel is cut off at its edge rather than scrolling sideways; the [commit diff window](#a-commits-diff-in-its-own-window) can wrap long lines instead.

## Diff types

FinderGit tries multiple diff strategies to show the most useful view:

1. `git diff HEAD -- <file>` — staged + unstaged changes combined
2. `git diff -- <file>` — unstaged changes only (fallback)
3. `git diff --cached -- <file>` — staged changes only (fallback)
4. For **untracked files** — shows the entire file content as "all added" (green)

## Text selection

You can select and copy text from the diff view for use in commit messages or code reviews.

## Open in Kaleidoscope

When [Kaleidoscope](https://kaleidoscope.app) is installed, an **Open in Kaleidoscope** button appears beside *Refresh Diff*. It opens the file's committed version against the one in your working tree, in a tab named for the file.

When Kaleidoscope is not installed the button is **not drawn at all**. A permanently greyed control advertising an app you have not bought carries nothing you can act on — a disabled control is for an obstacle you can remove.

### What each side holds

- **Left** — the file as it stands at `HEAD`, written out byte for byte. Binary files survive the trip intact, which is rather the point of sending them out at all: images are exactly what a dedicated viewer handles better than an inline one.
- **Right** — the file as it stands in your working tree.

The two cases where one side does not exist are handled rather than reported as an error. A **new** file has no committed version and a **deleted** one has nothing left in the working tree, so the missing side opens **empty**.

### Diff All — every change as one changeset

At the top of the file list in the **Changes** card, **Diff All in Kaleidoscope** sends every change at once — staged and unstaged, in the order the list draws them — as a single Kaleidoscope changeset rather than a tab per file. When the list is filtered to a directory, only that directory's changes go.

- **One document.** It opens whole or not at all, named for the repository, so a second repository's changeset in the same window is still told apart from this one.
- **Every side is pinned to one commit.** The committed side of every file is read from the same commit, so a commit or a branch switch while the files are being prepared cannot mix two baselines into one comparison.
- **Up to 400 files.** Past that FinderGit refuses with both numbers and suggests narrowing to a directory: a list that long is usually a build folder that slipped out of `.gitignore`, not a review.
- **What it leaves out, it names.** A directory, a submodule, a file Git can't hand over as a blob — each is listed under the button with the reason, and never stops the rest from opening.

### Finding Kaleidoscope

FinderGit looks in three places, so a copy that does not live in `/Applications` is still found: by bundle identifier wherever macOS has registered it, then the `ksdiff` command-line tool if you installed it, then the conventional application path.
