# Detail Panel

When you select a repository — in the [Repository List](/docs/repository-list) or the file browser — the detail panel splits into a **tab strip on top**, an **informational body in the middle**, and a **docked action bar pinned at the bottom**. Tabs hold the depth; the action bar holds the affordances that always need to be one click away.

![Detail panel showing the Overview tab — description, stars, topics, contributors, with Fetch/Pull/Push/Refresh docked at the bottom](/screenshot-detail-overview.png)

The tabs:

- **Overview** — at-a-glance facts about the repo (description, stars, topics, contributors, latest release) when it has a remote on a forge FinderGit reads, plus the [fork banner](/docs/github-integration#fork-awareness) when the repo is a fork
- **Unstage** — working-tree changes, the diff, the commit form (including the AI commit button)
- **Commits** — recent local history from `git log`
- **Branches** — local and remote branches, with one-click checkout
- **Release** — every tag beside the release cut from it, and what only exists on one side
- **Issues** — open issues on the repo's forge
- **Pull Requests** — open pull requests (merge requests on GitLab) on the repo's forge
- **Maintenance** — disk-space breakdown and cleanup (see [Repo Maintenance](/docs/repo-maintenance))
- **Trust** — the repo's auto-run surface (see [Repo Trust](/docs/repo-trust))

They read left to right by what they are about: what you are doing right now, then this repository's refs, then what the forge says about it, then looking after the place. Release sits beside Branches because a tag is a ref and the two answer the same kind of question.

The selected tab is filled with the colour its panel starts from, so the two read as one surface rather than a button above a card. The active tab is remembered across selections and across app launches, so the panel always opens where you left it.

## Docked action bar

The bottom edge of the panel carries:

- A compact **branch summary** — `branch · upstream · ↑N ↓M` (and stash count when non-zero), ending with **"Last fetched Xm ago"** so the background auto-fetch has visible evidence it's keeping the repo current
- The four repo-global actions: **Fetch · Pull · Push · Refresh**

Because the bar is docked outside the scroll area, the actions stay reachable from every tab — you don't have to leave Commits to push, or leave Issues to pull.

## Overview

The Overview tab paints the forge-side identity of the repo — GitHub, Codeberg, GitLab or Bitbucket; see [GitHub Integration](/docs/github-integration#what-populates-from-github) for what each forge can fill in:

- An **Open on GitHub** button — opens the repo's page in your browser. The label follows the remote's host (GitHub, GitLab, Bitbucket, or Codeberg) and it appears for any repo with a recognized remote, even before the rest of the metadata loads.
- **Description** at the top
- A row of stat pills: ★ stars · ⎇ forks · 🏷 latest release · 🔗 homepage. Stars and forks are read-only; the release tag opens the release page on the repo's own forge, and the homepage pill opens the configured homepage URL.
- **Topic chips** (wrapping onto multiple lines when there are many)
- **Top contributors** — up to eight avatars, click an avatar to open that user's GitHub profile

If the selected repo doesn't have a remote on a forge FinderGit reads (or the panel can't reach it), the section silently disappears and the tab shows a short hint pointing at where the operational view moved.

See [GitHub Integration](/docs/github-integration) for how to enable these tabs on GitHub, and what Codeberg, GitLab and Bitbucket fill in without any setup.

![Overview tab — the Open on GitHub button, stars and forks, and contributors for the selected repo](/screenshot-detail-overview.png)

## Unstage

This is where the working-tree affordances live. The Unstage tab holds:

- The **changes list** (staged and unstaged paths, with status markers)
- An inline **diff viewer** for the selected change (see [Diff Viewer](/docs/diff-viewer))
- The **commit form** with the AI Commit button (see [AI Commit Messages](/docs/ai-commit-messages))

This was previously folded into Overview; splitting it out keeps the informational and operational concerns separate.

![Unstage tab with changes list, inline diff, and the commit form](/screenshot-detail-unstage.png)

### Discard changes

Every unstaged row also carries a red **Discard**, and the section header a **Discard All** — the complement to Stage/Unstage when you want changes *gone* rather than staged:

- **Modified or deleted files** are reverted to the last staged/committed version.
- **Untracked files** are moved to the **Trash** — recoverable from Finder with "Put Back" — never deleted outright.

Both run behind a confirmation that states exactly what will happen, including the file count for Discard All. Discarding is destructive by nature; the Trash routing for untracked files is the safety net.

![Unstage tab with three unstaged changes — a red Discard on each row and Discard All next to Stage All in the header](/screenshot-discard.png)

### Stashed changes

Set the working tree aside without committing it. **Stash…** sits in the working-tree header beside Stage All and Discard All, because it is the third answer to the same question — what do I do with these changes right now — and the only one that is neither destructive nor a commitment.

It asks for a message and takes an empty one: leave it blank and git names the stash after your last commit. Untracked files go too, so the tree is genuinely clean afterwards rather than half-stashed. On a clean tree it says **"Nothing to stash"** instead of claiming it saved something — the direction that matters, since the other way round leaves you believing your work is tucked away.

Existing stashes appear underneath the commit form as **Stashed changes (N)**, collapsed until you open it. Each row carries the message, the branch it was made on, and how long ago — and a grey **Automatic** badge when the text is git's rather than yours, so a subject you never typed doesn't read as a description you chose.

Three actions per row:

- **Pop** — apply the changes and remove the stash
- **Apply** — apply the changes and keep the stash
- **Drop** — delete it without applying, behind a confirmation that says plainly that the changes are not applied first

If a pop hits a conflict, git writes the conflict into your files and **keeps the stash** — nothing is lost, and the entry stays on the list so you can try again after resolving. The panel refreshes to show the conflicted files, and the failure stays on screen rather than flickering past.

![The Unstage tab with the stash list open — two entries, one carrying a typed message and one badged Automatic, each showing its branch and age with Pop, Apply and Drop on the right](/screenshot-stash.png)

## Commits

A scrollable list of recent commits from local `git log`. Each row shows:

- The author's avatar on the left — resolved from their GitHub account (via the commit email) with a Gravatar fallback, or a colored monogram of their initials when neither is available
- The commit subject (up to two lines)
- Tag and branch badges when a ref points at the commit — **tags in gold**, branches and remote-tracking refs (`origin/main`, …) in grey, the current branch in the accent color
- The short SHA, author, and a relative date
- A copy button on the right that copies the full SHA to the clipboard — the icon flips to a green ✓ for ~1 second so the action has visual feedback

When the branch is **behind its upstream**, the commits a pull would bring in ride at the top in a distinct **"Incoming (N) · to pull"** card — each row marked with a ↓ — above your local history. So you see not just *that* you're behind, but *what* you're behind on. They're the commits from `git log HEAD..@{upstream}`, already on disk from the last fetch, so listing them costs nothing on the network. Pull, and the card folds away as they merge into the history below. Repos with no upstream — or already up to date — simply don't show it.

![Commits tab with an "Incoming (3) · to pull" card at the top — three behind-upstream commits marked with a ↓ and origin/main badges, set off above the local history, and "Last fetched now" in the docked action bar](/screenshot-commits-incoming.png)

### What a commit changed

Every commit row opens like a folder. Click the row — or the chevron on its left — and the files that commit touched unfold underneath it, with a **"N files · +additions −deletions"** summary on top and, per file, git's own status letter (**A**dded, **M**odified, **D**eleted, **R**enamed), the path, and that file's own line counts. A renamed file carries its old name underneath. Binary files say **binary** rather than pretending to a line count.

Click a file in that list and its diff for that commit opens in a sheet — the same viewer the working-tree diff uses, scoped to what this one commit did to this one file. That includes **deleted** files: what a commit removed is often the part most worth reading, and the whole deletion is there. Only binary files have no diff to show. It is read-only: nothing here stages, discards or reverts.

The list is fetched only when you open a row, so the tab still costs one `git log` no matter how much history you scroll. Merge commits list what they brought in against their first parent, rather than the empty list `git show` gives them by default.

![Commits tab with the newest commit opened onto its files — a "2 files +2" summary, then each path with git's status letter and its own line counts, tied to the commit above by a hairline](/screenshot-commit-files.png)

Hover any row to highlight it. Avatars and badges can each be turned off, and the number of commits shown (default **4**, up to **50**) set, in [Settings → Detail View](/docs/settings#detail-view).

![Commits tab — each row leads with the author's avatar on the left; commits pointed at by a ref show badges above the subject (gold tag, accent current branch, grey origin/master and origin/HEAD), followed by subject, short SHA, author, relative date, and a copy button](/screenshot-detail-commits.png)

## Branches

Switch branches without leaving the app — no more discovering mid-task that you were on the wrong one. Three ways in:

- **The branch chip** in the panel header shows the current branch; click it for a dropdown of the repo's local branches and switch with one click.
- **The Branches tab** is the full view. The **checked-out branch is pinned at the top** in its own card, with its upstream and its ↑ahead ↓behind counts beside it, so the one branch you are actually on never scrolls away. Under it, **Local** and **Remote** are separate bounded groups, each with a count, each row separated and highlighted under the pointer. Every row is a target: click anywhere on it, or use its **Checkout** button. Checking out a remote branch creates a local branch tracking exactly that remote — unambiguous even when several remotes carry the same branch name.
- **Right-click a repo** in the file browser → **Switch Branch** for the same quick switch from the list.

After a checkout the file tree, status badge, and branch chip all update automatically. If Git refuses the switch (typically uncommitted changes that would be overwritten), the error appears in the action-bar feedback — nothing is forced.

![Branches tab — Local and Remote sections with per-row Checkout, the current branch marked, and the branch chip in the header](/screenshot-branches.png)

### Worktrees

Under Local and Remote, the same tab lists the repository's **linked worktrees** — the folders `git worktree add` creates, each holding a second branch checked out on its own. They live here because a worktree *is* a branch checked out somewhere else, and because this is where you end up when Git refuses to delete a branch one of them is holding.

Each row shows the folder, where it is, and the branch it carries — or `detached` when it is not on one. A padlock marks a worktree you have locked, and a **missing** badge marks one whose folder is gone. The row menu offers **Add to Root Folders** (start working in it here), **Reveal in Finder**, and **Remove…**.

**Add** creates one. Give it a branch — new or existing — and the folder is created **beside** this repository, named `<repo>--<branch>`: the layout `git worktree list` expects, and the one that keeps `git status` clean, since a worktree nested inside its own repository shows up as untracked files.

**Prune** appears only when there is something to clear: a worktree whose folder you deleted by hand stays registered, and that registration is what keeps `git branch -D` failing on its branch.

Removal is never forced. Git refuses to remove a worktree holding uncommitted changes, and FinderGit shows you that refusal rather than overriding it — the branch is always kept, only the folder goes.

## Issues and Pull Requests

Both tabs share the same row shape:

- A GitHub-style state icon (filled circle for issues — green for open, purple for closed; pull-request arrows for PRs — green for open, grey for draft, purple for merged, red for closed)
- The `#number`
- The title (up to two lines)
- Coloured label chips
- The author's avatar on the right

### Reading a thread without leaving the app

Click anywhere on a row and it unfolds in place: the **description rendered as Markdown** — headings, lists, links, inline and fenced code — under the author and when they opened it, followed by the **comment thread**. A long description folds after the first stretch with a **Show more** link, so one verbose issue cannot push the rest of the list off screen. One row is open at a time.

On a **pull request** the preview shows the whole discussion, not just the conversation tab: the body a reviewer submitted with their verdict, and the notes pinned to lines of a file, each labelled for what it is. A pull request reviewed entirely inline — which is how most of them are — would otherwise look as though nobody had said anything.

The description costs nothing extra — every forge already returns it with the list. The comments are fetched only when you open a row, capped at the first 30, and cached for a minute like everything else in these tabs. That is the same on GitHub, Codeberg and Bitbucket; GitLab shows comments only to a signed-in user, so its preview says so instead (see [GitLab](/docs/github-integration#gitlab)).

**Images in a description are not downloaded.** An issue body is written by anyone who can open an issue, so every image URL in it is chosen by someone else — and fetching one would tell them your IP address and when you read their issue, or reach a service only your Mac can see. FinderGit shows a placeholder and leaves the fetching to your browser, which is what the **Open in browser** button is for.

Under the preview, **Open in browser** and **Copy link** are there for when you do want github.com — a permalink to paste into a message, or the parts FinderGit does not render yet.

![An issue opened in place — labels, the author and when they filed it, then the description rendered as Markdown with headings, inline code and a fenced block, folded behind Show more, with Open in browser and Copy link underneath](/screenshot-issue-preview.png)

Each tab's header has a **New Issue / New Pull Request** button (opens the corresponding "new" page), an **Open on GitHub** button (opens the full Issues / Pull Requests list page — the label follows the remote's host), and a **Refresh** button that bypasses the 60-second cache when you want fresh data.

On GitHub repos both tabs need either a working `gh` CLI (see [GitHub Integration](/docs/github-integration)) or a Personal Access Token in Settings. On Codeberg and GitLab they need nothing — both APIs answer anonymously. On Bitbucket only Pull Requests apply: its issue tracker was retired, and the Issues tab says so. For a repo with no remote, the tabs show a short explanation instead of an empty list.

![Issues tab — green open-issue icon, number, title, labels, author avatar, with New Issue, Open on GitHub, and Refresh in the header](/screenshot-detail-issues.png)

![Pull Requests tab on a Codeberg repository, needing no credentials — the top pull request opened in place with its description, the next one collapsed below, and New Pull Request / Open on Codeberg / Refresh in the header](/screenshot-detail-prs.png)

## Release

![The Release tab — tags on the left with their presence, releases on the right, a filter and the tag count in the header](/screenshot-detail-release.png)

Tags and releases side by side, because the states worth seeing are the ones where they disagree: a tag nobody cut a release from, a release whose tag is not in your clone, a tag that exists here and not on the remote.

**One row is one version.** The tag is on the left, the release cut from it on the right. They are cells of the same row rather than two lists, so they cannot drift apart as tag messages wrap — which is exactly what happens on a repository whose tag messages run to a paragraph.

A tag row shows whether it is **annotated** (a filled tag icon — its own object, carrying a message, a tagger and a date) or **lightweight** (an outline icon — just a name pointing at a commit). Releases are cut from annotated tags. The row ends with the date, the short commit id, a button to open the tag on its forge, and a ⋯ menu.

The line under the name is **not always the same sentence**, and which one it is matters. An annotated tag shows its own message. A lightweight tag has none, so it shows the subject of the **commit** it points at, behind a small commit mark and in a lighter grey. They were written by different people at different times, and a commit subject printed under the heading "tag message" is a caption that lies — so the row labels which one you are reading rather than quietly filling the gap.

### Where each tag actually is

`git tag` lists what is in **your clone**, which is not the same set as what is on `origin` — and the difference is invisible in every tool that shows you one list. A tag you made and never pushed looks identical to one everybody has. A tag a colleague pushed this morning does not appear at all until you fetch.

So every row says which of the three it is:

- **on both** — nothing to do; Push would be a no-op and deleting locally leaves origin's copy
- **local only** — it exists here and not on origin. This is the one Push is for
- **not fetched** — origin has it and you do not. There is no local tag to delete, and **Fetch** on the row brings it down

**Check remote** is what asks `origin`, and it is a separate button because it is the one thing here that touches the network — the tag list itself is local git and answers instantly. Until it has answered, no row claims either way: FinderGit will not tell you a tag is unpushed on the strength of a lookup it never made.

When the answer comes back with tags you are missing, the header offers **Fetch N tag** to bring all of them down at once. And each action is offered only where it can do something: Push appears on local-only rows, Fetch on not-fetched ones, and neither is drawn on a row where it would be meaningless.

### Finding one tag among hundreds

A long-lived repository can carry hundreds of tags — the count in the header is the honest number, and on a repository measured while building this it was over seven hundred. The **filter** field matches the tag name and **exactly what the row's second line says** — an annotated tag's message, or the commit subject a lightweight tag shows instead. So typing `rc` finds the release candidates, a word from a tag message finds the tag carrying it, and a word from a merge commit finds the lightweight tag sitting on it. The header says how many of the total are shown.

Both halves of that are deliberate. A filter that hides a row whose visible text contains what you typed is the worst shape a search can have — the words are on screen and the box says there is nothing there. Matching text the row does *not* show is the same fault wearing a friendlier face, and it returns rows with no visible reason to be there.

### Date or version — and why there is a choice

Rows are ordered **newest first, in one sequence**, whichever side supplies the date: a tag in your clone is dated by the tag itself, one you have not fetched by the release cut from it. So a tag pushed last week that you have never fetched sits at the top where it belongs, rather than in a block of its own after everything else.

That is the default, and on most repositories it is all you need. But "when was this tag made" is **two different questions** depending on the kind, and nothing on screen used to say so:

- an **annotated** tag is an object with a creation date, and that is the date you see;
- a **lightweight** tag is only a name. Git records nothing about when it was made — there is no such field — so the date shown is the **commit's**.

Which means a lightweight tag put on an older commit sorts below tags that look newer, and the list is correct while reading as though it were broken. On a real repository `v1.0.2` sat at the very bottom of two hundred rows, under `v1.0.1`, because the commit it names predates the `v1.0.1` tag object by six days.

So the header carries a **Date / Version** picker. Version order reads the names and nothing else, which also fixes the ordering that pure alphabetical gets backwards: `v26.10` belongs above `v26.2`, and a release belongs **above its own release candidates** — `v24.6.3` over `v24.6.3-rc.0`, not under it. Tags that are not version-shaped at all, a `latest` or a `stable`, are kept together at the end rather than interleaved among the numbers.

Hovering the date tells you which of the two it is, so a surprising position always has a visible explanation.

### Acting on many tags at once

Click a tag to select it, ⇧-click to extend the range, ⌘-click to add or remove one. A bar appears above the list with **Fetch**, **Push** and a **Delete** menu, and nothing changes until you use it. Each action applies to the part of the selection it can touch, and says how many that is — Push over five tags of which two are already on origin acts on three, and says three.

The three deletions live behind one menu rather than as buttons in a row: **Delete locally**, **Delete on the remote**, and **Delete everywhere**. The last one does both sides in one go, and it runs **the remote first** — deliberately. If the remote deletion fails, a protected tag or a permission denied, your local tag has not been touched and nothing is lost. The other order would destroy the only remaining reference to that commit and only then discover it could not reach origin. When a run does stop half way, the result says **which side** it stopped on, because the recovery differs: a tag still on origin needs the whole thing again, one already gone from origin only needs deleting here.

**The header and that bar stay put while the list scrolls.** On a repository with seven hundred tags you will often build a selection near the bottom, and chrome that scrolls away with the rows takes the actions for that selection with it.

The selection covers the tag, never the release beside it. **A tag and its release are two separate objects with an optional link**, in both directions: deleting a release leaves its tag standing, and a release can even be created for a tag that does not exist yet.

Deletions run one at a time and report **an outcome per tag**, not per run. Ten pushes where three fail will tell you which three and what Git said about each — "already exists" and "denied" are different problems with different fixes. The ones that did not go through stay selected, so retrying does not mean picking them again. **Stop** ends the run, and whatever had not been attempted is reported as exactly that rather than as a failure.

### What deleting a tag on the remote actually does

Worth knowing before you use it, because it is not what most people expect:

- Your **local** tag stays. Only the copy on `origin` goes.
- Anyone who has already fetched the tag keeps theirs.
- **If a release was cut from that tag, GitHub does not delete it — it turns it into a draft.** The release disappears from the public releases page and moves to an `untagged-…` URL.
- **Pushing the tag back does not undo that.** The release stays a draft until someone re-publishes it by hand.

FinderGit says which of these applies before you confirm, and it knows because the tab already pairs each tag with its release. A tag with no release gets the shorter, calmer sentence.

### Right-click

Both halves of a row carry a context menu, and they are different menus, because a tag and a release are different objects.

On the **tag** you get the same actions as the ⋯ button — Fetch, Push, Delete Locally…, Delete on Remote…, each only where it applies — plus **Open Tag on GitHub** (or GitLab, Codeberg, Bitbucket), **Copy Tag Link**, **Copy Tag Name** and, when the tag is in your clone, **Copy Commit SHA**. The same page is one click away on the row itself.

Those three appear only when the forge can be expected to *have* that page. On a tag marked **local only** — which is a measured answer, `origin` was asked and did not have it — they are not drawn at all, because a link into a 404 is worse than no link.

Right-clicking a tag that is part of a **multi-selection** gives you the actions for the selection, each labelled with the number it will act on. The deletions for the one row under the pointer are *not* repeated below them: two sets of delete items in one menu is not a scope you can read at a glance. What stays under the tag's own name is Copy, which cannot be ambiguous. This is also what macOS already does — right-clicking inside a selection in Finder acts on the selection.

On the **release** you get **Open Release in Browser**, **Copy Release Link** and **Copy Tag Name**. Nothing appears on a row that has no release.

### Releases

The right-hand column is read from the forge: the release title, **draft** and **pre-release** badges, an attachment count, when it was published, and a button to open it in a browser.

A badge appears only when the forge actually reported it. GitLab has no draft or pre-release concept at all, so nothing is drawn there rather than "published" being implied by a flag it never sent. **Bitbucket has no releases**, and the tab says so instead of showing an empty list under a heading.

A release whose tag is not in your clone is **not** an orphan: it gets an ordinary row, marked "not fetched", because the tag does exist — just not here. What lands in the separate section at the top is the genuinely stranded kind, typically a release left as a draft after its tag was deleted.

**"No release" is only ever said when it can be proved.** If the list came back short, or a refresh is in flight, or it failed, the count carries a **+** and no row asserts an absence — because the sentence matters: deleting a tag on GitHub turns its release into a draft, and a wrong "nothing else is affected" is how you find that out afterwards.
